# Real-binary evidence ledger, and a contradiction between two gate documents

Date: 2026-09-30
Status: **added a missing gate; found no product defect**

## The contradiction this session's work exposed

TASK-65 proved real bytes through three real tunnel binaries on the target OS. Then
the next step read `.agent/evidence/tunnel-matrix.md` — which is generated by
`scripts/test-method-matrix.ts` — and it said, of all nine methods:

> `realBinary` is false for every method … No tunnel binary was executed, no traffic
> crossed a tunnel … **the release gate stays shut.**

and rendered a hardcoded `**no**` in the Real-binary column for every row.

So the repository carried two gate documents making **opposite claims about the same
fact**, and the one asserting the weaker claim was the one a reader would reach for
when asking "was any tunnel actually proven?" A release decision resting on that file
would have been made on stale, and now false, information.

## Why the matrix could not see the truth

`realBinary` is not computed — it is hardcoded:

- `scripts/lib/method-contract.ts:118` — `realBinary: false` in the `MethodResult` the
  harness builds
- `scripts/test-method-matrix.ts` — renders `**no**` for every row unconditionally,
  and hardcodes `releaseComplete: false` at line 313

That is correct *about the harness*: it injects a process handle and genuinely cannot
execute a tunnel binary. But it had no way to represent real-binary runs performed
outside it, so the rendered document made a claim about the **world** that was no
longer true.

## What was added

### 1. `.agent/evidence/real-binary-evidence.json`

A machine-readable ledger of real-binary runs. An entry may only exist when a real
tunnel binary ran on the target OS and real bytes crossed the tunnel. Currently three
entries (GOST, FRP, XRAY) and an explicit six-method
`methodsWithoutRealBinaryEvidence` list, each with its reason:

- `SSH` — needs a real sshd target
- `PORT_FORWARD`, `DIRECT`, `REVERSE` — reach a **remote** node; none available
  (remote host/user/port/key values are `[REDACTED]`)
- `XUI` — metadata-only by design, runs no binary on our nodes
- `BACKHAUL` — installed and checksum-verified, but no client/server pair carrying
  traffic was run

### 2. `scripts/test-real-binary-evidence.ts` — 51 assertions

Registered in the aggregate runner. It guards three things:

1. **Structure** — required fields present and non-empty.
2. **Honesty** — the two lists must be an *exact partition* of the nine methods. A
   method may not appear in both, and may not be silently dropped from **both**. This
   is what stops a method quietly disappearing from the record.
3. **No overclaim** — `trafficCrossed: true` requires checks that actually cite
   carried data (a `\d+ ->` hop chain, `HTTP 200`, or `HELLO-XR`); `reconnect: true`
   requires a note naming a restart/recovery outcome; each entry's evidence file must
   exist, mention the method, **and** contain substantiating run evidence; each target
   must name a concrete Ubuntu version and record systemd.

It deliberately does **not** assert that all nine have real-binary evidence. That gap
is recorded, not papered over.

### 3. `scripts/test-method-matrix.ts` — renders from the ledger

The Real-binary column now reads `yes (no here)` for a method proved on the target and
`**no** (no here)` otherwise — separating *this harness's* result from *real-binary
evidence*, which the previous single `**no**` conflated. If the ledger is unreadable
the matrix says so explicitly and the suite **fails**; it never silently degrades to
"nothing proved".

The old "Why no method is marked complete … the release gate stays shut" section was
replaced with an explicit 3/9 statement naming the proved methods and the reason for
each unproved one.

## Mutation testing

Five mutants of the ledger, plus two of the matrix's ledger handling:

| # | mutation | result |
|---|---|---|
| M1 | `trafficCrossed: true` with checks that only say "process started" | **killed** — "cites evidence that bytes actually crossed the tunnel" |
| M2 | `XUI` dropped from both lists | **killed** — partition + count checks |
| M3 | `reconnect: true` with an empty note | **killed** — "reconnect claim names a restart/recovery outcome" |
| M4 | `XRAY` evidence pointer → `tunnel-matrix.md` | **killed after the check was tightened** (see below) |
| M5 | `GOST` present in both lists | **killed** — overlap check |
| M6 | ledger file absent | **killed** — "the real-binary ledger is readable" |
| M7 | `runs: []` (3 methods vanish from the partition) | **killed** — 3 failures |

**M4 initially survived and the check was weakened by it.** `tunnel-matrix.md` names
all nine methods in its per-method suite list, so a bare "does the file mention the
method" test passed while the file recorded no tunnel traffic whatsoever. The check
now also requires the evidence file to contain substantiating run content. Re-run: M4
killed, baseline still 51/51.

**A false "mutant survived" reading, corrected.** M7 was first reported as surviving
(51 passed). It had not: `node -p` fails with `stdin is not a tty` in this MSYS shell,
so the mutation was never written to disk — the suite was re-running against the
unmutated ledger. Applying the mutation through Python and re-running gave **3
failures**. The partition check was sound all along; my measurement was broken. Worth
recording because "node -p silently no-ops" will otherwise keep producing phantom
mutation results here.
