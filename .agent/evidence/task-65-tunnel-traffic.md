# TASK-65 — tunnel traffic and reconnect, executed on the target OS

Date: 2026-09-30
Status: **PASS** (real binaries, real TCP bytes, on Ubuntu 22.04.5 LTS amd64)

## Evidence type

Privileged Docker containers running the exact target OS with **systemd as PID 1**
(`/sbin/init`), not a remote VPS. `xt22` = Ubuntu 22.04.5 LTS x86_64. Binaries came
from the project's own `scripts/install.sh` into `/var/lib/xistance/bin`:
`backhaul`, `frpc`, `frps`, `gost`, `xray` (versions verified on target).

## What was proved

### 1. GOST — PASS

Two chained listeners forwarding real bytes through two gost hops to an origin
server that returns a known body:

```
gost -L "tcp://:19099/127.0.0.1:19098"
gost -L "tcp://:18080/127.0.0.1:19099"
```

```
1-hop  19099->19098        body=b'HELLO-XR'  PASS
2-hop  18080->19099->19098 body=b'HELLO-XR'  PASS
```

This is the **exact command form the product generates**: `buildGostCommand()` in
`packages/tunnel-core/src/config/gost.ts` emits `gost -L <proto>://:<port>/<host>:<port>`.
Getting traffic through therefore also validates that builder.

### 2. FRP — PASS, after fixing a real defect

Config was generated by the product's own builders (`buildFrpPair`), with the input
first parsed through the real Zod schema (`FrpConfigSchema`), then run through the
actual `frps` 0.70.1 / `frpc` 0.70.1 binaries installed by `scripts/install.sh`.

First run **failed to start at all**:

```
frps: field "allowPorts": cannot unmarshal string into types.PortsRange
frpc: login to server error: dial tcp 127.0.0.1:17000: connect: connection refused
```

frps typed `allowPorts` as `[]types.PortsRange` — an array of `{start, end}` objects —
while the product emitted the schema's plain strings. The Foreign node therefore never
bound its control port, so **every FRP tunnel failed to come up**.

Ground truth established against the real binary, not assumed:

| emitted shape | frps 0.70.1 |
|---|---|
| `allowPorts = ["18081"]` (what the product emitted) | REJECTED |
| `allowPorts = "18081"` | REJECTED |
| `allowPorts = "18081,18082"` | REJECTED |
| `allowPorts = [18081]` | REJECTED |
| `allowPorts = { start = 18081, end = 18081 }` | REJECTED |
| `allowPorts = [{ start = 18081, end = 18081 }]` | **STARTS** |
| `[[allowPorts]] start/end` | **STARTS** |

**Fix:** `packages/tunnel-core/src/config/frp.ts` gained `portsRange()`, which expands
a schema port string (`"80"` or `"6000-6100"`) into `{ start = N, end = N }`. A
malformed range now throws at generation time instead of emitting a config frps
rejects, so the operator gets a diagnosable error rather than a dead tunnel.

After the fix, on the same target OS:

```
frps: [probe] tcp proxy listen port [18081]
frps: new proxy [probe] type [tcp] success
frpc: login to server success
frpc: [probe] start proxy success
traffic through frps:18081 -> frpc -> origin:18081 -> HTTP/1.1 200 OK body=b'HELLO-XR'  PASS
```

### 3. XRAY — PASS

Client config generated by the product's own `buildXrayConfig()` and run with the
product's own `buildXrayCommand()` (`xray run -c <path>`); a matching vmess server
inbound was written for the peer side. Both instances started cleanly:

```
Xray 26.3.27 started   (client, product-generated config)
Xray 26.3.27 started   (server)
traffic: HTTP/1.1 200 OK body=b'HELLO-XR'  PASS
```

**Two probe-harness errors were diagnosed and corrected during this run — neither
was a product defect:**

1. `Top-level await is currently not supported with the "cjs" output format` in the
   scratch harness (rewritten with an explicit `main()`).
2. `SyntaxError: f-string expression part cannot include a backslash` — nested quoting
   in a `docker exec` heredoc; the probe was written to a file instead.
3. Xray initially timed out. Its `sniffing.destOverride` rewrote the destination from
   my probe's placeholder `Host: x` to `tcp:x:19098`. xray's own debug log proved the
   tunnel was working (`accepted tcp:x:19098 [xistance-server-in >> direct]`) — the
   probe was sending a hostname xray legitimately honoured. Sending the real
   destination in `Host:` made it pass. This is correct `sniffing` behaviour.

### 4. Reconnect — PASS

The panel supervises tunnel processes with systemd `Restart=on-failure`, emitted into
every tunnel unit by `packages/tunnel-core/src/process.ts:156` (the release unit
template `scripts/lib/service-unit.sh:102` uses the same policy). That mechanism was
proved on the target OS rather than assumed:

1. frps started under systemd: `active`, `MainPID=2774`, `policy=on-failure`
2. frpc registered a real proxy; traffic flowed: `body=b'HELLO-XR' PASS`
3. `kill -9 2774` — the supervised process was destroyed
4. traffic confirmed **down** (exit non-zero), so the tunnel genuinely died
5. systemd restarted it: `recovered after ~3s: new MainPID=2798 (old was 2774)`
6. traffic resumed automatically with **no operator action**:
   `frp-after-restart: HTTP/1.1 200 OK body=b'HELLO-XR' PASS`

```
systemd: Main process exited, code=killed, status=9/KILL
systemd: Scheduled restart job, restart counter is at 16.
RESULT: PASS (killed tunnel process recovered automatically, traffic resumed)
```

The panel's own API was exercised on the target OS through a real authenticated

through that API requires a **reachable SSH node** (`NodeConfigSchema` needs

So the tunnels proved above were launched from **the product's own generated
configs and the product's own command forms**, executed as real supervised processes
on the target OS. They are not panel-API-driven deployments. That distinction is
stated here rather than blurred.

## Harness defects found and fixed (not product defects)

- `pgrep -f "<pattern>"` inside a `bash -lc` one-liner matches the shell running it,
  so the kill loop killed its own shell (exit 143, twice). Patterns moved into a
  script file; `pgrep -x` used instead.
- The installer colourises its output, so a credential scraped from the log keeps a
  trailing ANSI reset (`admin@xistance.local\x1b[0m`). Left in, login returns 401.
  Fixed in the harness with an ANSI strip. **No secret value is recorded in this
  file, in any log, or in any test fixture.**
- Splitting `Admin password: SECRET` on the first `:` yields ` password: SECRET`;
  the value must be split on `": "`.
