# TASK-32 evidence — REVERSE method coverage

**Status:** passed

## The finding: a live `ssh -R` was reported as `running` when nothing could reach it

This is the acceptance criterion that mattered, and it was entirely unimplemented.
`GatewayPorts` appeared in exactly two places in the whole repository — both
READMEs. No code anywhere detected it.

The failure mode is quiet and expensive. With `GatewayPorts no` (the Debian and
Ubuntu default) OpenSSH does **not** fail the forward. It binds the remote
listener to loopback and carries on:

- the `ssh` process is alive and healthy,
- the remote port *is* listening,
- `computeStatus` sees one live process and returns `running`,
- nothing outside the Foreign host can connect, and no error exists anywhere.

An operator acting on that status loses traffic with no signal to act on.

## Fix: `packages/tunnel-core/src/reachability.ts` + engine wiring

A pure, dependency-free classifier plus the engine plumbing to actually call it.

| Observed remote state | Reported |
|---|---|
| bound to `0.0.0.0` / `::` / unknown | `running` |
| bound to a specific public address | `running` |
| bound to loopback, **public requested** | `degraded` + `GatewayPorts` named + remedy |
| bound to loopback, **loopback requested** | `running` — a deliberate choice, not a fault |
| not listening at all | `degraded` |

The last two are the distinctions that matter. Flagging a deliberate loopback
bind would train operators to ignore the warning; a live process with a
loopback bind must never produce `running`.

Wiring: `Runtime` gained a `reverseProbe` target, populated at deploy time;
`computeStatus` consults it after the liveness check and downgrades to
`degraded`, publishing a diagnostic whose summary names `GatewayPorts`. Results
are cached for 30s and invalidated on lifecycle changes, so changing
`GatewayPorts` on the Foreign host is picked up without a restart.

### The module was nearly another `selectForwardStatus`

`reachability.ts` was written and unit-tested, and was **dead code** — not
exported, not called. That is the exact failure TASK-30 found with
`selectForwardStatus`, so §11 of the suite exists specifically to test the
*engine* path, not the pure function: a loopback listener must yield `degraded`,
`0.0.0.0` must yield `running`, and the diagnostic must name the cause.

### Probe failure must not downgrade

If the probe is unavailable — no `ss`, unreachable node, permission error — a
working tunnel must stay `running`. Downgrading on an indeterminate result would
show every reverse tunnel as degraded on a constrained host and destroy the
signal's value. Covered by an explicit case, and mutation-tested (mutant C).

## Other defects fixed

**1. `reverseToSshConfig` did not trim the host.** `cfg.host.trim()` decided
*whether* to fall back, but the untrimmed value was returned. `" 203.0.113.9 "`
passed the truthiness test and became the ssh destination with its spaces
attached.

**2. Unvalidated REVERSE fields.** `username`, `host`, `forwardHost` and
`remoteBindAddr` were all bare `z.string()`, and all four reach an ssh argv
token. The same RCE shape TASK-29 closed for SSH tunnels was still open through
this path: a leading-dash `username` would be read by `ssh` as an option.

`username` and `host` now carry the SSH destination patterns; `forwardHost` and
`remoteBindAddr` share a `hostLikeAddress` schema (extracted from DIRECT's
`directAddress`, which had the identical problem for the same reason — both are
spliced into one delimited string).

`ReverseConfigSchema.protocol` was already `z.literal("tcp")`, so UDP was already
rejected; that is asserted rather than changed.

## Errors made, recorded because they changed the outcome

**A broken mutant counted as a kill.** Mutant H was generated by deleting the
line containing the username regex, which left unbalanced braces. It died with
an esbuild syntax error, not an assertion failure — and under a pipe the
broken run even reported `exit=0`. I had been treating non-zero as a kill.
Regenerated as a whole-chain replacement (H2), which fails 3 assertions
cleanly, and I now capture the real exit code before writing files.

**My fixture returned the wrong shape.** The production probe pipes
`ss -ltnH` through `awk '{print $4}'`, so the runner's stdout is the bare
`127.0.0.1:8080` token. My fake returned a full `ss` line, which the parser
correctly rejected — and I briefly read that as "the probe isn't wired in".

**`exitCode`, not `code`.** The `Runner` result field is `exitCode`; my fake
returned `code`, so every `which ssh` lookup read as a failure and the deploy
died on a missing-tool error.

**A schema that crashed instead of failing.** Two cases fed the schema values it
should refuse. With the validation correctly in place, `mk()` threw before the
assertion could run. Both now use raw objects, which is also the correct layer:
the trim and the fallback live in `reverseToSshConfig`, so they are tested
there.

**`.default()` before `.regex()`.** Zod's `.default()` returns a `ZodDefault`,
which has no `.regex`, so the module failed to load. Validation first, default
last.

## Not claimed

- **No live sshd was involved.** The reachability probe is driven by a fake
  runner; the classifier is pure. Real `GatewayPorts yes`/`no` behaviour on a
  live Foreign host is unproven and remains outstanding VPS evidence.

  seconds to be reflected, or a restart. Documented, not eliminated.
