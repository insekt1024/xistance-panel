## Why it cannot be rebuilt here

The arm64 payload is not built by a script in this repository — it is produced by
`docker buildx build --platform linux/arm64` (per `task-80-arm64-build.md`), and
`stage-arm64-artifact.ts` only *stages* the result from `dist/arm64-stage`.

Running it now:

```
> [builder 18/18] RUN npm run build:
  0.499 exec /bin/sh: exec format error
ERROR: failed to solve: process "/bin/sh -c npm run build" ... exit code: 255
```

`exec format error` means the host cannot execute the aarch64 binary: **binfmt-qemu
is not registered.**

```
$ ls /proc/sys/fs/binfmt_misc/
ls: cannot access '/proc/sys/fs/binfmt_misc/': No such file or directory
```

`buildx ls` advertises `linux/arm64` as a *platform*, but with no emulation
registered that is a claim, not a capability — the same distinction TASK-112 draws
between an emulated result and a native one.

## Both routes need something this host does not have

| route | requirement | available? |
| --- | --- | --- |
| native arm64 build | a real `linux/arm64` builder | no — both contexts are the local Windows engine |
| emulated arm64 build | binfmt-qemu registered | no — needs `--privileged` container |

The amd64 build needs neither: x86_64 is native, which is why it built, staged,
archived, verified, and installed on both targets today without incident.

## What I did NOT do

I did not re-run the binfmt registration. It was blocked pending approval and I
am not retrying a blocked command. Even with it, the result would be an
**emulated** arm64 build — which TASK-112 already established cannot be installed
(the QEMU GNU tar defect reproduces on a 192-byte archive), so it would not close
the native-arm64 gate anyway.

**Re-enabling emulation would produce a green-looking artifact that still could
not be installed on real hardware.** That is worse than an honest stale artifact,
because it moves the failure from visible to deferred.

## The correct route

The release workflow's own arm64 job runs on `ubuntu-24.04-arm`:

```yaml
${{ matrix.runner_arch == 'arm64' && 'ubuntu-24.04-arm' || 'ubuntu-latest' }}
```

That is a native arm64 runner, which builds the payload and runs the installer
for real. Reaching it needs the commit and tag that TASK-109/110/111 have been
blocked on, so this is not a separate blocker — it is the same one.

## Consequence for release readiness

The amd64 artifact is current, verified, and installed on both target OSes. The
arm64 artifact is **stale and must be regenerated by CI**. It must not be
published as-is: it would ship all 16 legibility defects, including the 200% text
failures, on the architecture the PRD requires.
