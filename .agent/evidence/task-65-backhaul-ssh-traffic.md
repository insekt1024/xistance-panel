# Real-binary evidence: BACKHAUL and SSH (TASK-65, 2 of the 6 remaining methods)

Date: 2026-09-30
Target: **Ubuntu 22.04.5 LTS, amd64, systemd PID 1** — privileged Docker container
`xt22` (image `xt-target:22.04`). This is exact-OS container evidence, **not**
remote-VPS evidence.
Binaries: the ones `scripts/install.sh` pinned, checksum-verified into
`/var/lib/xistance/bin` (`backhaul` v0.7.2, OpenSSH client from the distribution
repository).
Credentials: **throwaway probe values generated inside the container.** No real
host, user, port, key, or token appears here; all such values are `[REDACTED]`.

Result: **BACKHAUL 10/10, SSH 6/6.**

## BACKHAUL — 10/10

Configuration was generated by the **product builder**
(`buildBackhaulConfig()` in `packages/tunnel-core/src/config/backhaul.ts`), not
hand-written. Server and client both came from the product:

```toml
# server
[server]
bind_addr = "127.0.0.1:19100"
transport = "tcpmux"
token = "PROBE_TOKEN_PLACEHOLDER"
ports = ["19101=19098"]
nodelay = true
keepalive_period = 75
heartbeat = 20
channel_size = 2048
mux_con = 8
log_level = "info"
```

| # | assertion | evidence |
|---|---|---|
| 1 | no stale backhaul before the run | `pgrep -x backhaul` empty |
| 2 | origin service reachable | `127.0.0.1:19098` → `HELLO-XR` |
| 3 | server alive | pid 4877 |
| 4 | client alive | pid 4897 |
| 5 | control channel established | `control channel successfully established` |
| 6 | listening on the exposed port | `listening on address: [::]:19101` |
| 7 | **traffic crossed the tunnel** | `127.0.0.1:19101` → tunnel → `127.0.0.1:19098` → `HELLO-XR` |
| 8 | wrong-token client refused | `failed to receive control channel response` |
| 9 | legitimate traffic unaffected by the refused client | still `HELLO-XR` |
| 10 | **reconnect** | client killed → traffic stopped → recovered on restart (pid 4897 → 4969) |

**Token enforcement (assertion 8).** v0.7.2 does not log "auth failed". A client
presenting the wrong token gets no usable control channel: the server never
accepts it and the client times out reading the response
(`failed to receive control channel response: … i/o timeout`). The probe asserts
that observable outcome rather than a log string that does not exist. It also
asserts the legitimate client keeps working afterwards, so the refusal is
isolation rather than a shared-fate outage.

## SSH — 6/6

A **real `sshd`** was installed and started in the container, and the tunnel was
driven by the **exact argv the product emits** from `buildSshCommand()`:

```
ssh -N -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes \
    -o StrictHostKeyChecking=accept-new \
    -L 127.0.0.1:19110:127.0.0.1:19098 -p 22 probeuser@127.0.0.1
```

(plus `-i <throwaway key>` and `-o BatchMode=yes`, which the engine supplies.)

| # | assertion | evidence |
|---|---|---|
| 1 | origin service reachable | `127.0.0.1:19098` → `HELLO-XR` |
| 2 | real sshd running | pid 4785 |
| 3 | **traffic crossed the forward** | `127.0.0.1:19110` → sshd → `127.0.0.1:19098` → `HELLO-XR` |
| 4 | **reconnect** | forward killed → traffic stopped → recovered (pid 4791 → 4820) |
| 5 | leading-dash username refused | `BLOCKED` |
| 6 | no ProxyCommand side effect | marker file absent |

**Assertion 5 carries a control.** The probe requires the product validator to
reject `-oProxyCommand=touch …` **and** to accept `probeuser`. Without that
control a validator rejecting everything would pass the check vacuously. The
validator exercised is the shipped `ssh.ts`, transpiled — not a copy of it.

## Three harness defects found and fixed while gathering this

Recording these because each one produced a **false verdict**, and two of them
first looked like product defects.

**1. An empty config file, blamed on the product.** The first run failed all six
process assertions with
`[FATAL] neither server nor client configuration is properly set`. That reads
exactly like a FRP-style config defect. It was not. `cat -A` on the container
file printed **nothing** — the file was 0 bytes. A `docker cp` that ran before
`mkdir /tmp/probe` had silently left an empty file, and the `||` fallback
branch masked it. Investigating the key names *in the real binary*
(`grep -ao 'toml:"[a-z_]*"'` on `backhaul`, which listed `bind_addr`,
`remote_addr`, `transport`, `token`, `ports`, `channel_size`, `mux_con` …) showed
the product's keys were all correct and accepted individually.

**2. A self-inflicted empty file.** The CRLF strip was written in place —
`tr -d '\r' < "$f" > "$f"` — which truncates the file before reading it. The
host-side configs were empty too, with the same empty-file SHA-256
(`e3b0c442…`). Lesson: **never redirect into the file you are reading**; write to
a temp name and move. Every staged file is now byte-compared host↔container
before use.

**3. A stale client invalidated the reconnect test.** With a `backhaul` client
left over from an earlier run still holding the exposed port, killing the "new"
client changed nothing, so the probe reported `during='HELLO-XR'` — a
connectivity failure reported as *success*. The probe now `pkill -x backhaul`
before the run (exact-name: a `-f` pattern matches the probe's own command line
and kills the probe), and asserts traffic actually **stopped** before asserting
it recovered.

**Also:** two fixed `sleep`s were replaced with bounded polls. The control channel
and the restarted tunnel are established asynchronously, and a fixed delay
asserts against a race. The retry-bounds suite had the same shape of bug.
