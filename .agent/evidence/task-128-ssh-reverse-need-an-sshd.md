# TASK-128 — SSH and REVERSE now generate from the product's builders; the peer is missing here

**Status: fixtures done and correct. Execution BLOCKED by an environment limit, not a
product defect: the target has no `sshd` and no network to install one.**

## What was built

`scripts/gen-traffic-fixtures.ts` now emits SSH and REVERSE through the same
builders the panel calls, so neither is hand-written:

```json
SSH:     ["ssh","-N","-o","ServerAliveInterval=30", ..., "-i","/root/.ssh/id_ed25519_traffic",
          "-L","127.0.0.1:18104:127.0.0.1:19098","-p","22","root@127.0.0.1"]

REVERSE: ["ssh","-N","-o", ..., "-i","/root/.ssh/id_ed25519_traffic",
          "-R","0.0.0.0:18106:127.0.0.1:19098","-p","22","root@127.0.0.1"]
```

REVERSE is generated by running `reverseToSshConfig()` -- the exact mapping
`engine.ts` uses -- and then `buildSshCommand()` on the result. That is what makes it
a proof of REVERSE rather than a second hand-written argv that could drift. The
`-R` in that output is the evidence the mapping did its job.

The key path is a throwaway generated **in the target**, so no credential from the
repo or the environment is ever involved.

## The blocker

`/usr/sbin/sshd` is not installed on xt24, and it cannot be:

```
$ apt-get install -y --no-install-recommends openssh-server
rc=100
E: Failed to fetch http://archive.ubuntu.com/.../openssh-server_9.6p1-3ubuntu13.19_amd64.deb
   Temporary failure resolving 'archive.ubuntu.com'
```

The target container has no DNS/network. So SSH and REVERSE cannot execute here.

## Why this is not a product gap and not a test gap

- Both `-L` and `-R` argv are **exactly** what the product emits; they are generated,
  not transcribed.
- TASK-65 already proved both methods carry real traffic on a target OS. That probe
  lived in a container that ran an `sshd`; this one does not.
- The product's own `install.sh` installs `openssh-client`, and REVERSE's builder
  comment says the Foreign node needs a real sshd. So an sshd is an operator
  prerequisite, not something the panel provides.

## What closes it

Any one of:

1. a target image with `openssh-server` baked in (no network needed at run time);
2. run the harness on a host with an sshd reachable on 127.0.0.1:22;
3. bind-mount an `sshd` binary plus its host keys.

Until then the shell suite SKIPs these two with that reason, and
`test-real-binary-evidence.ts` continues to report SSH and REVERSE as lacking a
runnable data-path test. **I am not widening the allowlist to make it green.**
